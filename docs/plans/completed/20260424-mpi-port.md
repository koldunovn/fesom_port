## Overview

Take the C port from a single-rank serial code to a multi-rank MPI code that
can run on partitioned meshes. Goal: pi mesh on 2 and 8 ranks producing
single-rank-equivalent results (bit-identical for un-reduced fields, ulp-level
relative drift ≤ 1e-12 for reduced fields), then CORE2 on 16+ ranks stably
integrating with PHC IC + JRA55 forcing + SSS restoring + runoff.

The Fortran model has been MPI-aware since v0; the existing partition files in
`<mesh>/dist_<NPES>/` are reused unchanged. We mirror the Fortran data
structures (`T_PARTIT`, `com_struct`) and call sites, but collapse the 50+
shape-specific Fortran exchange variants into 4 generic C functions templated
on (field-kind, n_levels, n_components).

The pre-MPI code keeps working (`./fesom_port` with 1 rank == today's serial
run, identical numbers) — we add MPI on top, not as a replacement.

## Development Approach

- **testing approach**: regression-oriented. We don't have a unit-test framework, so each task ends with a "must-pass" runtime check (e.g. "halo exchange identity test: fill interior with rank-id, exchange, halo == neighbor rank-id").
- complete each task fully before moving to next; build & test after each
- mark `[x]` immediately when done
- update plan if scope shifts mid-task
- bit-equivalence to single-rank run is the only validation that matters; halo bugs are silent until they aren't
- intermediate "MPI-debug" mode: a build flag (`FESOM_HALO_NUKE`) that fills halo entries with NaN before each halo exchange, so any read of stale halo immediately propagates as NaN
- MPI is a hard dependency once introduced (no `#ifdef HAVE_MPI`) — Fortran is the same way; Levante always has MPI

## Testing Strategy

- **Halo identity test** (slice 30b): fill `field[interior_n] = rank_id`, exchange, check `field[halo_n] == owning_rank_id`. Plus a negative test that deliberately corrupts a halo entry to confirm the assertion fires.
- **Single-rank vs serial parity** (slice 30c): run `mpiexec -np 1 ./fesom_port` (synthesised partit, no file reads) and compare to today's serial binary, snapshot-by-snapshot — must be **bit-identical**.
- **2-rank parity** (slice 30h): run `mpiexec -np 2 ./fesom_port` vs single-rank; expected behaviour:
  - Bit-identical for fields **not** touched by Allreduce (e.g. T, S after pure advection if no integrate_nod corrections fire)
  - **ulp-level relative drift (≤ 1e-12)** for fields downstream of CG dot products and integrate_nod sums, because `MPI_Allreduce(MPI_SUM)` has implementation-dependent summation order — this is the only legitimate source of non-determinism, **not** FCT or anything else algorithmic
  - For aggressive parity tests: a debug build using `MPI_Reduce` to root + sum in fixed order + `MPI_Bcast` (slow, deterministic) can be added if any drift looks suspicious
- **8-rank pi**: must run 1000 steps without blowup, snapshots compared visually.
- **CORE2 16-rank**: must run 200 steps without blowup with PHC + JRA55 + SSS + runoff.

**Acceptance tolerances** (concrete):
- Bit-identical: byte-for-byte equal in the snapshot NetCDF for un-reduced fields
- ulp-relative: `|x_mpi - x_serial| / max(|x_serial|, 1e-30) < 1e-12` for reduced fields

## Technical Details

### Generic exchange signature

```c
typedef enum {
    FESOM_HALO_NOD2D,        /* uses partit->com_nod2D, single-level */
    FESOM_HALO_NOD3D,        /* uses partit->com_nod2D, n_levels per node */
    FESOM_HALO_ELEM2D,       /* uses partit->com_elem2D */
    FESOM_HALO_ELEM3D,       /* uses partit->com_elem2D, n_levels per element */
    FESOM_HALO_ELEM2D_FULL,  /* uses partit->com_elem2D_full (extended halo) */
    FESOM_HALO_ELEM3D_FULL,  /* same with levels */
} fesom_halo_kind;

void fesom_halo_exchange(real_t          *field,
                         fesom_halo_kind  kind,
                         int              n_levels,
                         int              n_components,
                         fesom_partit    *partit);
```

Field layout: `field[entity * n_levels * n_components + lev * n_components + comp]`.

For 2D scalar: `n_levels=1, n_components=1`. For UV elem3D: `n_levels=mesh->nl, n_components=2`.

### Partition file format (already verified)

```
my_list<NNNNN>.out: 8 integer headers + 3 integer arrays (nod, elem, edge)
com_info<NNNNN>.out: 3 com_struct blocks (nod2D, elem2D, elem2D_full),
                    each with rPEnum, rPE, rptr, rlist, sPEnum, sPE, sptr, slist
```

Both are line-oriented ASCII with whitespace separation. Read with `fscanf` against integer tokens.

### Ordering of arrays in `myList_*`

Fortran convention (preserved):
- `myList_nod2D[1..myDim_nod2D]` are the interior nodes (this rank owns them)
- `myList_nod2D[myDim_nod2D+1 .. myDim_nod2D+eDim_nod2D]` are the halo nodes (owned by another rank, but this rank needs them for stencils)
- Same for elem2D (with eDim_elem2D + eXDim_elem2D for full halo)

So for any rank-local index `i` in `[0, myDim+eDim)`, the global id is
`myList_*[i]` (1-based in Fortran, we'll subtract 1).

### Send / recv buffer sizes (allocated once, reused)

- max send size = max over all sender PEs of (sptr[k+1]-sptr[k]) × max(n_levels) × max(n_components) × sizeof(real_t)
- max recv size = max over all receiver PEs of (rptr[k+1]-rptr[k]) × … (same)
- For real-world numbers: pi 8-rank typically <100 nodes per neighbor, CORE2 16-rank up to ~5000

### Hard MPI dependency

We don't try to keep an `#ifdef` for non-MPI builds. The `fesom_mpi.c` shim
becomes a real MPI wrapper. This matches Fortran (always compiled with MPI).
On a single-rank `mpiexec -np 1`, behavior is identical to today's serial code
because all halo dimensions are 0 and Allreduce on 1 rank is a no-op.
